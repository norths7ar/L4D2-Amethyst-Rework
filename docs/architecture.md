# 配置架构笔记

面向维护者，记录基于 Competitive Rework 的配置分层、组件职责与设计原则。本文不专属于任何模式；具体玩法由配置和实现表达，变更记录见 [更新日志](CHANGELOG.md)。

## 配置调用链

```text
configs/matchmodes.txt：注册模式 ID 和显示名
  → cfg/cfgogl/<mode>/
      → shared_cvars.cfg：模式身份、mutation、Stripper 与共同规则
      → confogl_plugins.cfg：插件加载清单或有序 exec 子清单
      → confogl.cfg / confogl_off.cfg：进入与退出模式
      → mapinfo.txt：地图例外
```

插件加载清单可以直接加载，也可以按命令缓冲限制拆分为有序子清单。清单只负责插件生命周期命令与 `exec`；玩法 CVar 放在规则配置中。

## 分层与权威位置

| 层 | 负责什么 | 典型入口 |
| --- | --- | --- |
| 服务器相关 | 不随模式改变的网络、日志与服务器设置 | `cfg/server.cfg` |
| 通用修复 | 无关模式的引擎修复 | `cfg/generalfixes.cfg` |
| 模式注册 | 模式 ID 与显示名 | `configs/matchmodes.txt` |
| 模式规则 | mutation、插件组合、参数与退出收尾 | `cfg/cfgogl/<mode>/` |
| 地图例外 | 地图配置与实体调整 | `mapinfo.txt`、Stripper |
| 运行时调整 | 有生命周期的临时覆盖 | 对应组件 |

修改规则前先确定权威来源，避免同一参数被多层隐式覆盖。配置（如有）声明目标值，控制器选择和下发参数，执行组件负责实际行为；配置选择不应顺带混入无关的插件重载和状态变化。

## 插件目录与共享实现

以 `addons/sourcemod/` 为基准，插件按功能职责归类。PVP／PVE 表示玩法，对抗／战役表示游戏内基准模式，两者不混用；目录按玩法职责划分，不据基准模式判断归属。

| 插件位置 | 职责 |
| --- | --- |
| `plugins/` 根目录 | 不依赖具体玩法模式、需要服务器级生命周期的底层功能 |
| `plugins/fixes/` | 启动和退出模式后仍需加载的公共修复 |
| `plugins/anticheat/` | 默认加载的反作弊功能 |
| `plugins/optional/` | 按需加载的共享功能、机制与修复 |
| `plugins/optional/fun/` | 装饰与娱乐功能 |
| `plugins/optional/competitive/` | 依赖玩家特感、双方队伍或竞技计分规则的专用功能 |
| `plugins/optional/coop/` | PVE 专用规则和流程 |
| `plugins/disabled/` | 明确停用的插件 |

SourceMod 自动加载会递归扫描普通子目录，跳过 `optional/` 和 `disabled/`。按需插件放在 `optional/` 内；玩法专用修复归对应玩法目录。进入模式时框架卸载后按 CFG 重建插件组合，退出模式后恢复自动加载集合；目录归属不代替加载清单，也不意味着所有模式启用。

源码入口原则上与 SMX 使用相同相对目录；`scripting/include/` 和插件私有模块是编译依赖，不对应独立 SMX。移动时同步更新各模式的加载引用，保持加载顺序；目录变更本身不增加或减少模式加载的功能。

同一功能优先维护一份当前实现。可通过既有配置表达的差异继续由模式配置选择；真正不同的规则、接口或界面可以保留独立实现。

版本统一应同时核对命令、ConVar、native／forward、配套资源和生命周期。

## 按完整职责划分插件

插件边界以完整功能为单位，而不是把同一种行为按地点或触发时机分散给多个插件。例如，起点、沿途和终点的资源替换属于同一类规则，不应分别由准备插件、安全区插件和地图清理插件各自决定。

| 组件职责 | 负责的内容 |
| --- | --- |
| 地图资源规则 | 资源之间的替换、刷新限制、可拾取次数与临时放行 |
| 区域识别 | 判断起点、终点或其他区域，向调用方提供位置事实 |
| 玩家装备 | 开局装备、跨章节携带与随身物品整理 |
| 物品使用效果 | 使用后的治疗量、恢复效果等行为 |
| 菜单与投票 | 展示选项、收集决定，并调用规则所属组件 |
| 生命周期管理 | 发布准备、开局、换章节、换战役等状态变化 |

区域识别提供事实，规则组件决定如何使用这些事实。暂时不区分位置的规则可以直接统一处理，将来需要位置差异时再接入区域信息，无需提前增加空洞的分层。

观察到事件的组件不因此拥有所有后续策略。例如，战役切换组件通知新战役开始，资源组件自行清除战役范围的临时设置；菜单也不另存一份资源状态。

## Stripper 与运行时规则

Stripper 适合表达地图机关、按钮、事件连接、实体布局及地图专属修复。跨地图统一的资源禁用和替换由资源组件维护，避免模式规则散落在大量地图文件中。

地图专属补给调整也可以是完整的地图设计。例如，“删除随机补给，再设置固定补给”是一组关联修改；判断时应结合来源、注释和上下文，不能仅因使用了整类删除就移除其中一半。已有明确意图的补给布局、终局修复和弹药堆调整，应作为整体保留，发现具体问题后再审视。

资源替换需要尊重地图行为：目标名、位置、父子关系、事件输出和剩余触发次数都可能参与机关逻辑。资源类别变化不应顺带切断这些关联。

## 生命周期与组件职责

Competitive Rework 管理插件锁定、模式切换与逆序卸载；自定义模式沿用框架入口。`load_unlock`、`unload_all`、`load_lock`、`refresh` 由框架生命周期统一安排。

临时调整须说明覆盖哪一层、作用于谁，以及何时失效。人数档位、章节和战役是不同的作用范围，各自的重置应由对应生命周期驱动。

功能组件负责自身状态及退出清理。组件之间通过明确接口或事件协作；接管旧职责时同步退出原执行路径，避免多个插件反复扫描、删除或重新赋值来维持同一条规则。

重构优先复用已有有效逻辑、注释、玩家文案和交互。职责迁移与玩法调整应分清：前者保持可观察行为，后者需要明确的设计决定。

## 源码与编译产物

以 `addons/sourcemod/` 为基准，`scripting/` 的插件入口尽量与 `plugins/` 使用相同相对路径；跨模式共用源码可放在 `scripting/optional/`。`include/` 和插件私有模块目录不对应独立 SMX。

当前维护入口使用 `<name>.sp`；历史副本使用 `<name>.<version>.sp`，分支副本使用 `<name>.<来源>-ver.sp`。

## 修改时的阅读顺序

1. 从模式注册和加载链确认组件是否实际生效。
2. 确定配置权威位置，再阅读组件的事件、状态与退出路径。
3. 地图问题同时检查地图配置、Stripper 和地图自身脚本。
4. 新增或替换插件时核对 `configs`、`data`、`gamedata`、`translations`、VScript 与模型等配套资产。
5. 切换后残留先查退出和卸载职责，不先堆补救定时器。

编译检查源码依赖，配置变更核对实际引用；插件加载、玩法和生命周期效果需结合服务器日志与实际运行判断。
